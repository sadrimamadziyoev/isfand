# Техническое задание
## AwareGuard MVP Lite — Платформа симуляции фишинга

**Версия:** 1.0  
**Тип:** Web Application  
**Срок разработки:** ориентировочно 7–10 рабочих дней  
**Команда:** 1 Backend + 1 Frontend разработчик  
**Назначение:** Проверка продуктовой гипотезы на 3–5 корпоративных клиентах.

---

## 1. Цель проекта

Разработать минимальную веб-платформу, позволяющую проводить согласованные учебные фишинговые кампании среди сотрудников компаний и получать результаты их взаимодействия с письмами.

MVP должен обеспечивать полный цикл:

**Загрузка сотрудников → Выбор шаблона → Отправка писем → Отслеживание переходов → Отображение результатов.**

Основной пользователь системы — администратор AwareGuard, который самостоятельно управляет кампаниями клиентов.

## 2. Технологический стек

| Компонент | Технология |
|---|---|
| Backend | Python 3.12+, FastAPI |
| Frontend | React, TypeScript |
| UI Library | Ant Design |
| Database | PostgreSQL 16 |
| ORM | SQLAlchemy, Alembic |
| Email | SMTP-релей компании |
| Deployment | Docker Compose |
| API | REST API, JSON |
| Authentication | Логин, пароль, MFA |

Архитектура: Modular Monolith.

## 3. Функциональные требования

### 3.1. Авторизация администратора

- Вход по email и паролю.
- Обязательная двухфакторная аутентификация.
- Выход из системы.
- Защищённые сессии.
- Один тип пользователя — Platform Administrator.

Регистрация пользователей через интерфейс не требуется.

### 3.2. Управление компаниями

Администратор может:

- Создавать компанию.
- Указывать название и корпоративный домен.
- Сохранять подтверждение полномочий на проведение симуляций.
- Подтверждать владение доменом через DNS TXT.
- Просматривать список компаний.
- Блокировать компанию и её кампании.

Отправка разрешается только после подтверждения домена, полномочий и согласования почтовой инфраструктуры.

### 3.3. Управление сотрудниками

Функции:

- Выбор компании.
- Загрузка списка сотрудников через CSV.
- Просмотр списка.
- Удаление или исключение сотрудника.
- Валидация email.
- Исключение дубликатов.

Формат CSV:

`full_name,email,department`

Пример:

`Ivan Ivanov,ivan@company.example,IT`

Для MVP поддерживать до 500 сотрудников в одной компании.

### 3.4. Шаблоны писем

Реализовать 3 встроенных учебных шаблона:

1. Уведомление о корпоративном документе.
2. Уведомление от внутреннего HR-сервиса.
3. Уведомление о внутренней IT-заявке.

Поля шаблона:

- Название.
- Тема письма.
- HTML-содержимое.
- Учебная ссылка.
- Описание признаков фишинга.

Конструктор HTML и загрузка произвольных вложений не нужны. Использовать вымышленные или разрешённые клиентом бренды.

### 3.5. Создание кампании

Поля:

- Название кампании.
- Компания.
- Шаблон письма.
- Список сотрудников.
- Дата создания.

Статусы:

- Draft.
- Approved.
- Running.
- Completed.
- Stopped.
- Failed.

Перед отправкой должна выполняться тестовая отправка, затем подтверждение кампании вторым уполномоченным лицом. Для MVP это может быть подтверждение вне системы с сохранением имени согласующего, времени и документа-основания. Самостоятельное утверждение без независимого подтверждения запрещено.

### 3.6. Рассылка писем

Система должна:

- Отправлять письма через согласованный SMTP-релей клиента.
- Использовать только разрешённые адреса отправителя.
- Добавлять уникальную ссылку для каждого сотрудника.
- Фиксировать результат отправки.
- Ограничивать скорость отправки.
- Позволять немедленно остановить кампанию.

**Ограничения:** отправка только сотрудникам подтверждённой компании, не более 500 получателей на кампанию. Повторная проверка разрешений выполняется непосредственно перед отправкой каждого письма.

### 3.7. Отслеживание действий

Фиксировать следующие события:

- `email_sent` — письмо принято SMTP-релеем.
- `email_failed` — ошибка отправки.
- `link_clicked` — подтверждённый переход по ссылке.
- `training_viewed` — открыта обучающая страница.

Система должна отличать обычные переходы от автоматических обращений почтовых сканеров. Неподтверждённые переходы не должны засчитываться в Click Rate.

Каждое событие связывается с компанией, кампанией и сотрудником через уникальный случайный токен.

В MVP не реализуется сбор введённых паролей, OTP, cookie или других секретов.

### 3.8. Обучающая страница

После перехода сотрудник видит:

**«Это была учебная симуляция фишинга».**

Страница содержит:

- Краткое объяснение произошедшего.
- Признаки подозрительного письма.
- Советы по информационной безопасности.
- Рекомендацию сообщать о подозрительных письмах в ИБ.

Страница должна корректно отображаться на компьютерах и смартфонах.

### 3.9. Dashboard

Отображать:

- Количество сотрудников в кампании.
- Количество отправленных писем.
- Количество ошибок отправки.
- Количество сотрудников с подтверждёнными кликами.
- Click Rate в процентах.
- Количество сотрудников, открывших обучающую страницу.

**Формула:**

Click Rate = Уникальные сотрудники с подтверждённым кликом / Успешно отправленные письма × 100%.

Дополнительно таблица:

| Сотрудник | Email | Отправлено | Кликнул |
|---|---|---|---|
| Ivan Ivanov | ivan@company.example | Да | Да |
| Sara Karimova | sara@company.example | Да | Нет |

Персональные результаты доступны только уполномоченному администратору.

### 3.10. Экспорт результатов

Реализовать кнопку **Export CSV**.

Поля отчёта:

- Компания.
- Кампания.
- Сотрудник.
- Email.
- Статус отправки.
- Наличие подтверждённого клика.
- Время события.

PDF и XLSX не требуются.

## 4. Структура базы данных

Основные таблицы:

1. `companies`
2. `company_domains`
3. `employees`
4. `email_templates`
5. `campaigns`
6. `campaign_recipients`
7. `tracking_events`
8. `admin_users`
9. `audit_logs`

Все данные компаний должны быть изолированы по `company_id`. Проверки доступа выполняются на backend и в PostgreSQL через Row-Level Security.

## 6. Нефункциональные требования

- HTTPS для всех соединений.
- Хеширование паролей Argon2id.
- Секреты SMTP вне исходного кода и базы данных в открытом виде.
- Валидация входных данных.
- Защита от SQL Injection, XSS и CSRF.
- Непредсказуемые токены отслеживания.
- Проверка полномочий и домена перед каждой отправкой.
- Ограничения скорости отправки и публичных endpoint.
- Журнал действий администратора.
- Резервное копирование PostgreSQL.
- Изоляция данных разных компаний.
- Ограниченный срок хранения персональных данных, согласованный с клиентом.
- Отсутствие критических и высоких уязвимостей перед реальным пилотом.

## 7. Что не входит в MVP

- Личные кабинеты клиентов.
- Регистрация компаний.
- Платёжная система и тарифы.
- AI и ML-модели.
- Конструктор шаблонов.
- SMS-фишинг.
- Мобильное приложение.
- Микрокурсы и тестирование знаний.
- Интеграции с Active Directory.
- SSO.
- Автоматические повторные кампании.
- Сложные дашборды и Risk Index.
- White Label.

## 8. Этапы реализации

**День 1–2:** Backend, PostgreSQL, авторизация, компании.

**День 3–4:** Импорт сотрудников, шаблоны, создание кампаний.

**День 5–6:** Утверждение, SMTP, отправка, отслеживание.

**День 7–8:** Обучающая страница, Dashboard, CSV-отчёт.

**День 9–10:** Тестирование, исправление ошибок, развёртывание.

Срок ориентировочный. Выход на реальных получателей допускается только после проверки безопасности и подтверждения разрешений.

## 9. Критерии приёмки

MVP считается технически готовым, когда:

1. Администратор может создать компанию и подтвердить разрешения.
2. CSV со 100 сотрудниками успешно импортируется.
3. Можно выбрать шаблон и создать кампанию.
4. Без утверждения кампания не запускается.
5. Нельзя отправить письмо на неподтверждённый адрес.
6. Письма успешно отправляются через согласованный SMTP.
7. Подтверждённые клики корректно записываются.
8. После клика отображается обучающая страница.
9. Dashboard показывает корректную статистику.
10. CSV-отчёт соответствует данным PostgreSQL.
11. Остановка кампании предотвращает последующие отправки.
12. Пройдены тесты безопасности и изоляции компаний.

## 10. Проверка бизнес-гипотезы

Пилот провести в 3–5 компаниях.

Измерить:

- Сколько компаний согласились участвовать.
- Насколько быстро проводится одна кампания.
- Насколько полезна аналитика для ИБ.
- Сколько компаний хотят повторить проверку.
- Сколько компаний готовы оформить платную подписку.

**Целевой результат:** минимум одна компания подтверждает готовность платить после пилота.

---

**Итоговый результат разработки:** работающая веб-платформа с одной административной панелью, загрузкой сотрудников, учебными email-кампаниями, отслеживанием результатов, обучающей страницей и CSV-отчётностью.
